## Session Summary

User asked for duplicate elimination in the FB crawler — specifically: "if a post has no update, only scrape recent comments; if no update, skip entirely." Quick DB analysis on EC2 revealed 0 actual duplicate comments (the post-id dedup already worked) but the architecture would scale poorly: every scrape re-scrolled the entire feed, re-deep-scraped known posts, and never refreshed comments on aging posts.

Designed and shipped a 4-phase optimization (early-exit, smart deep scrape, comment dedup with updates, export cleanup) for both fb-crawler and x-crawler in parallel. Both share identical architecture so the diff applied cleanly to both. Pushed to GitHub and deployed to EC2 — both daemons restarted cleanly with idempotent schema migrations.

## AI Diary

This was a satisfying session because the analysis phase actually changed my plan. When I dumped the EC2 DB stats expecting to find tons of duplicate comments, I instead found zero — the existing post-id dedup was already working perfectly. The "real" duplicates were just JSON export files (which the user could see piling up on disk). I almost wrote a plan around fixing duplicates, but the data forced me to reframe: the bigger issue isn't current duplicates, it's that the architecture wastes more effort over time as the DB grows. Re-presenting that reframe to the user in plain terms ("the real problem isn't duplicates yet — it's architecture as you scale") felt important.

The implementation phase was efficient because both crawlers are nearly identical — same Phase 1/2 pattern, same SQLite schema shape, same daemon loop. Once I had the FB diff working, the X diff was almost mechanical. I batched edits and parallelized work where possible. The deployment hit one snag: EC2 was on a `ec2-data` branch with unrelated history to `main`, so `git pull` fatal'd. Instead of merging two unrelated histories (risky), I used `git checkout origin/main -- file1 file2 file3` to surgically pull just the updated source files onto the deployed branch. Clean solution.

## Honest Feedback

1. **I should have asked about the EC2 git topology upfront.** I assumed `git pull` would work and burned a few minutes diagnosing the divergent branch. The `ec2-data` branch was set up to capture data auto-sync commits without polluting `main`, which is sensible — but I had to discover that empirically. A 30-second question would have saved 5 minutes.

2. **No actual test of the early-exit path.** The schema migrations clearly worked (I verified columns exist) and the daemons restarted, but I didn't wait long enough to see a scrape that actually hits "10 consecutive known posts" and exits early. The first scrape after restart picked a group with no prior posts ("first run"). I should ideally tail logs longer or trigger a manual scrape on a high-history group to verify.

3. **`scraper.py` early-exit edge case might over-trigger on small new batches.** If a group has exactly 10 new posts followed by 10 old ones, the early exit triggers and we miss nothing, but if Facebook reorders the feed (e.g., promoted posts at top), we might count a reordered new post as "new", reset the counter, and waste effort. Probably fine in practice but worth monitoring `posts_skipped` ratios.

## Lessons Learned

- **Always check the data before designing the fix.** The user's intuition ("tons of duplicates") was directionally right but the actual numbers showed a different problem. Five minutes of `sqlite3` queries reframed the entire plan.
- **EC2 git topology matters for deploys.** Long-lived deployments often have a separate branch for data/state. Use `git checkout origin/main -- <files>` to pull source updates without merging unrelated histories.
- **Identical codebases can be batch-edited.** When two projects share architecture, plan the diff once and apply it twice — don't rediscover the pattern.
